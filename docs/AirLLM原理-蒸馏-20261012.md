## 一、一句话原理

**模型骨架建在 PyTorch 的 `meta` 设备上（只有形状、没有数据），给每一层挂前/后钩子：进这层前把它的权重从分片读上来 materialize 到 GPU，算完立刻扔回 `meta` 并 `empty_cache()`。** 显存峰值 ≈ **一层**，与模型总大小无关。

---

## 二、四个机制（逐个带行号）

**① 钩子驱动，不是外层循环** —— `airllm_base.py:748-774`
每层 `register_forward_pre_hook(self._pre_hook)` + `register_forward_hook(self._post_hook)`；`_pre_hook:879` 加载+搬运，`_post_hook:896` 算完 `module.to('meta')`。**它没改 transformers 的 forward，是挂钩子。**

**② 异步预取默认开** —— `__init__:86` `prefetching=True`，docstring 逐字 *"overlap the next layer's disk load with the current layer's compute"*；`_pre_hook:890-894` 用线程池 `self._executor.submit(self._load_streamed_layer, nxt)` 提前抓下一层。

**③ MoE 是"把层再切到专家级"** —— `airllm_kimi_k3.py:13-15` 逐字：
> Each layer holds **896 experts** and routes a token to **16** of them, so the experts are streamed individually rather than by layer: expanded, a layer's experts are **~55GB** but a token needs **~1GB** of them.

实现：给**每个专家模块**各挂一对钩子（`airllm_base.py:841-854`），`_expert_pre_hook:856` 只读那个专家的张量（`load_layer_subset(..., keys)`），`_expert_post_hook:862` 逐个参数扔回 `meta`。**不是"整层不用搬"，是把粒度压到专家。**

**④ 超大嵌入表走磁盘 mmap** —— `utils.py:119-123` 注释：Qwen4-Exp/Flash-Next 那张 ~51B 的 n-gram 表（约 102GB 主机内存装不下）**流进 file-backed mmap，从磁盘 gather 行**；`tie_word_embeddings` 时把 embedding **常驻 GPU**（`airllm_base.py:752-762`）。

## 三、🔴 代价（源码自证）——**含一条必须纠正的说法**

| 说法 | 源码说什么 |
|---|---|
| **"不靠大内存运行"** | ✅ **真**。README:286 逐字：*"The trick: AirLLM only ever keeps one layer on the GPU at a time, so the VRAM you need depends on the model's layer size — not its total size."* 数字表 README:295-297（70B 全精度 ~4GB / 405B ~8GB / 671B ~12GB）；Kimi K3 **3.72GB VRAM**（README:38，写明在 RTX 6000 A[da] 上端到端实测）。 |
| **"速度远超传统大模型"** | ❌ **反的**。机制上每生成一个 token 都要把整模型（或活跃专家）从分片重读一遍（`_pre_hook` 每次 forward 都 `load + move`，`_post_hook` 每次 `to('meta') + clean_memory`）⇒ **瓶颈从算力换成磁盘/PCIe 带宽**。**它是拿速度换内存。**（源码里**没有任何"更快"的表述**；"慢多少"我没实测，不编数字。） |
| **"不需要量化"** | ⚠️ **半真半假**。真：省显存靠流式，你不必为省显存去量化。假：它**自带落盘量化**（`utils.py:470-489`：`'4bit'`→`bnb.quantize_nf4(blocksize=64)`；`'8bit'`→`quantize_blockwise(blocksize=2048)`），且 `_should_load_verbatim:636-640` 逐字写着 *"加载时解压会让**单层占用涨约 4 倍**，**这正是 Kimi-K3 级 checkpoint 塞不进单卡的原因**"* ⇒ **它不但用量化，还靠"保住量化态不被解压"才塞得下。** |
| **"对输出质量有帮助"** | ❌ **无关**。它只搬内存，不碰输出质量。**"不幻觉/不胡说"不由它提供** —— 那是"能力位＝器官 + 自证读数"那套架构的活。**两条目标别混成一条。** |

## 四、对 V8 能融合什么 / 不能融合什么

**能融合（不要卡、纯算）**：**「切分与显存预算」**——读 checkpoint 的 `*.index.json` → 算每层多大、单层峰值显存、分片计划、MoE 是否值得走专家级。这是"压缩"里**能量得出数**的那一半，也是 `utils.py:528-572 split_and_save_layers` 那套切分的原理版。

**不能只靠它解决的**：**速度**（它的机制注定 IO 密集）、**输出质量/不幻觉**（它不碰）。⇒ 它**不是"任督二脉"的全部**，它只打通"显存"这一条。

**真跑那半的硬约束**：仓里 `train_recipe` 能力位逐字写着「**本机零算力 ⇒ 不接真训练**」；且主人 **2026-10-11 令「本地不要大模型」**（本机 ollama/llama/vllm 进程实测 0 个）。⇒ 真要跑，只能在云上（RunPod），且要主人发钥匙/放钱。
