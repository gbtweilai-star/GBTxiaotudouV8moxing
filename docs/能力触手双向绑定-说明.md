## 二、绑定类型（三类 · **空白才报红**）

每条能力位恰好是下面**三类之一**：

| 绑定类型 | 判据（写在工具 `RULES` 里，可复核、可改） | 现读数 |
|---|---|---|
| **触手承载** | `gbt_allinone/api.py` 里该能力位的**分派分支导入了触手本体模块**（`tentacle` 整包 / `tentacle.omni_*` / `omni_*` / `vision_cap`）—— **代码证据**，不是拍脑袋 | **9** 条 |
| **直连** | 该能力位由框架本体模块实现、分派分支**未**导入触手本体 ⇒ **显式的第二类绑定** | **231** 条 |
| **未绑** | 既非触手承载、又无承载载体（空白冒充绑好）⇒ **报红并逐条点名** | **0** 条 |

> **「直连 ≠ 未绑」**是本口径的关键：不经触手本体的能力**必须显式记成「直连」**，
> 并写下承载载体与依据；**空白**才算未绑。这样「零遗漏」判据才有意义 —— 它查的是
> **有没有谁被漏掉**，不是"是不是都走了触手"。

**本体模块 → 触手域**的映射按 `omni_*` 文件自己的命名：`omni_mouse`→点击、`omni_fs`→文件、
`omni_read`→读屏、`omni_web`→读网、`omni_audio`/`wasapi_loop`/`silero_vad`→听觉 …
导入「整只手」（`tentacle` / `tentacle.bridge` / `tentacle.omni_core`…）⇒ 绑到**全部 10 个域**。

> 🔴 一个实测教训（已写进代码注释）：**必须按全路径匹配**。
> `from .llm import bridge` 的最后一段也是 `bridge`，若只取最后一段，`llm_status` 会被
> 误判成「触手承载」—— 真相是仓里有两条 `bridge`（`tentacle/bridge.py` 与 `llm/bridge.py`）。

## 三、能量怎么绑（两级证据 · 分得清「确定」与「证据」）

能量侧的核心是 **`gbt_allinone/llm/cloud_llm.py::_KEY_CHAIN`**（`key_gateway` 自报
`chain_source = llm/cloud_llm.py::_KEY_CHAIN（同源同序）`）。13 条通道逐条绑到能力位上，
用**两级证据**，**分开记 `basis`**：

| 级别 | 判据 | 现读数 |
|---|---|---|
| **权威声明级** | `security/policy.py::evaluate(kind, {})` 给该能力位声明了 `external_llm` 作用域 ⇒ 它**确定**要过密钥链 | **8** 条（codex_chat、codex_models、codex_turn_send、autopilot、llm_chat、think_loop、sec_llm、devour_pulse） |
| **代码证据级** | 承载模块文本里出现**链本身的符号**（`cloud_llm` / `key_gateway` / `_KEY_CHAIN`）⇒ 它**会碰**密钥链 | **15** 条（key_gateway、multimodal_port、genoffice_bridge、llm_status、freellmapi、vision、hf_voice、zimage_rewash、policy_delta、spend_guard、thebrain_bridge、ui_render、tentacle、tentacle_manifest、tentacle_status） |
| 不触链 | 其余能力位：**不经能量链**（面板里写「—（不经能量链）」） | 217 条 |

> 🔴 收窄过一次（教训写进代码）：早先把 `external_llm` / `密钥链` 这类**词**当标记，
> 结果把 `security/policy.py`（只是**声明**作用域）也算成"用能"⇒ 假绿。现在只认**链的符号名**。

**用能的能力位**绑到的通道 = **现读可用的腿**（当前 9 条）；`active` = `nvidia-flash`。
链是**共享池**（`key_gateway` 自己也这么报 `shared_quota_keys`），所以「谁在承载谁」按
「**可用的腿共同承载用能的能力位**」记，`key_gateway` 的自述口径不另发明一套。

### 🔴 未探测不画成通

13 条通道里有 **4 条不是「可用」**：`custom`（未声明 base_url）、`anthropic`（密钥不在位）、
`gemini`（密钥不在位）、`potato`（已禁用·曾报 401/403）。这 4 条的**承载 cap 数一律记 0**，
面板里标为「不可用/未探测」并置灰；**判据里有一条专门查**「不可用通道却承载着 cap」= 报红。

## 四、双向自洽怎么核

**两个方向都各自列出来，再互校**（不是从一边推算另一边了事）：

1. **正向**：`cap → 承载触手域`（每条能力位一行，见台账 `caps[].tentacle_domains`）。
2. **反向**：`触手域 → 承载哪些 cap`（每个域一行，见台账 `tentacle_domains[].caps`）。
3. **互校**：把反向逐域反演回 `cap → {域集合}`，与正向**逐条比对**；
   不一致的记进 `orphans.mismatch_cap_vs_domain`，**逐条点名**。
   能量同理：`orphans.mismatch_cap_vs_channel`。
4. **越界**：能力位引用的触手域必须**在总纲里**、能量通道必须**在 13 条链里**；
   否则记 `orphans.caps_bad_domain` / `caps_bad_channel` ⇒ 报红。
5. **标签层**（框架自己的触手语言）：每条能力位的 kind 与 `domain:<域>` 都必须在
   `_valid_labels()` 里（反向 = 「能力位无触手标签」）；不一致记 `label_face`。

现读：**无未绑 / 无幽灵通道 / 无不可用通道冒充承载 / 两个方向的反演一致** ⇒ 零遗漏判据全绿。

## 七、硬性纪律（本件怎么守）

- **不许假绿**：探不到就写「未探测」并写明为什么；绑定算不出来就报红，**不许留空当"绑好了"**。
- **未探测不画成通**：不可用的能量通道**不得**被算作承载着谁（有专门判据 + 负对照）。
- **只读探测**：只 `import` 模块 + 读注册表/配置；**不执行框架动作、不调任何需要授权的作用域**。
  能量走 `key_gateway.energy()/run("status")` 这类**读类直连**，不铸钥、不落盘、不外发。
- **页面自包含**：零远端引用、无 `fetch`/`XHR`/`eval`、无 `<iframe>`、无 `type="module"`，
  数据只走**经典脚本** `energy-data.js`。
- **判据带负对照**：`--check` 共 **15** 条判据 + **10** 条负对照（掏空能力边 / 一条能力不绑 /
  绑到不存在的触手域 / 绑到不存在的能量通道 / 不可用通道画成承载 / 反演不一致 / 能量边读不到 /
  外链注入 / 数据脚本改 module / 标签层读不到）—— **喂坏必须报红**，否则判据自身报红。
