# 穿透式交叉扫描增强 · 立项与交付

> 开发者：自由的风 · GBT小土豆V8 · 本署名不可删除、不可篡改归属
>
> **立项令**（Owner 2026-09-27）：「给扫描器加一套强制钩子与交叉验证机制，彻底堵死遗漏。」
> 排序：**排在穿透网之后、编排内核之前**。走今日规矩：开护照 → 改 → 用例 → 独立复核 → 关账。

**一句话**：**触手到位必须钩住；钩不住 = 失败；同一目标至少两路互扫；覆盖率不到 100% 就补扫；每一次都留痕。**

---

## 一、取证三问（先取证，再动手 —— 全部现读源码/实测）

| 问 | 答案（2026-09-27 现读） |
|---|---|
| 现有扫描器有没有钩子机制？ | **没有 per-触手强制钩子**。`tools/codex-scripts/boot-selfcheck.py` 与 `gbt_allinone/tools/code_exhaustive_scan.py` 里 grep `hook` 零命中；本仓的"留痕"是**结果层**惯例（各能力自报 `source_kind=`），不是"到位必钩、不钩即失败"的机制层。⇒ 本立项补的正是这一层。 |
| 触手池是否支持并发调度？ | **有先例，无通用池**。`quick_scan.py:1185` 用 `ThreadPoolExecutor(max_workers=12)` 压 NTFS stat（注释：stat 是 I/O 密集，线程池有效）；`deploy-panel.py:852` 用 6。⇒ 本引擎沿用同款 `ThreadPoolExecutor`，默认 **8**，可调。 |
| trace_store 是否支持 `source_kind="cross_scan"`？ | `source_kind` 是**本仓留痕惯例字段**（现存 `feishu` / `absorb` / `cloud_pc` / `publish` 等各能力专属值）；`trace_store` 能力位本体是**只读**的（五张表只读清点）。⇒ 本引擎**不写 trace_store**，写自己的追加式账 `state/cross_scan_trace.jsonl`，每条 `source_kind="cross_scan"`，与 `trace_store` 的读侧口径一致、互不越权。 |

## 二、架构（六模块 · 与立项令一一对应）

```
① 扫描控制器  decompose()      —— 目标拆成原子单元（bindings: 每资产一件 / registry: 全表一件 / tree:<dir>: 每文件一件）
② 触手集群    spawn_and_hook() —— 虚拟按需生成：单元 × 读法 = 一根触手（有界并发，默认 8）
③ 钩子池      hooks_for()      —— 每类单元 ≥2 路**独立读法** + 1 路仲裁读法；钩子触发 = 读到观察值并留证
④ 交叉验证    cross_validate() —— 多路指纹比对；不一致 → 请第三路仲裁，少数服从多数
⑤ 遗漏检测    detect_omission()+覆盖率 = 已钩住/总数；<100% 有界补扫（默认 2 轮），仍钩不住**如实报**
⑥ 审计与门禁  _trace()         —— 每次扫描追加 state/cross_scan_trace.jsonl（无痕即未发生）
```

**步骤锁**（`StepLock`）：`decompose → spawn → hook → cross_validate → detect_omission → trace` 六步，
**跳步/乱序当场抛 `StepViolation`**（不许带病继续、不许静默改序）。

**亿万触手口径（诚实，不虚报）**："亿万"指的是**可扩展的生成模型**——触手 = 单元 × 读法的笛卡尔积，
按需生成、用完回收；**实际并发受 `max_workers` 与物理机限制**（本机默认 8）。
本次满量级实测：**4348 单元 × 2 路 = 8696 次触手执行**。

## 三、五条红线（写死 · 每条都有对应用例）

| # | 红线 | 实现 | 用例 |
|---|---|---|---|
| 1 | **钩子未触发 = 任务失败** | 观察值为空/异常 → `status="unhooked"`，不计入 hooked | 幽灵单元用例（见 §四负控 2） |
| 2 | **步骤锁必须生效** | `StepLock.enter()` 严格按序 | 负控 1：跳步被拒 |
| 3 | **交叉验证必须进行** | 每单元 ≥2 路独立读；指纹不一致 → 仲裁 | 正控：registry 两路一致（导入 vs 文本解析） |
| 4 | **遗漏必须补扫** | 覆盖率 <100% → `detect_omission` 有界补扫 2 轮 | 负控 2：幽灵补扫两轮仍缺 ⇒ 如实报 missing |
| 5 | **每次扫描写 trace** | `state/cross_scan_trace.jsonl` 追加式 | `report` 读数 |

## 四、实测读数（2026-09-27 · 全部真跑）

### 正控（应 100%）

| 目标 | 单元 | 覆盖 | 一致 | 仲裁 | 遗漏 |
|---|---|---|---|---|---|
| `registry`（注册表 180 位） | 1（全表） | **1.0** | 1（导入读法 = 文本解析读法**逐指纹相同**） | 0 | **0** |
| `bindings`（触手账） | **4348** | **1.0** | **4348** | 0 | **0** |

> `registry` 那条尤其值钱：它证明**注册表导入 == 源码文本解析**（两条完全不同的读法给出同一指纹）——
> 这正是"交叉验证"该有的样子：不是把同一句话读两遍，而是两把不同的尺子量同一件事。

### 负控（必须抓住，抓不住就是装饰）

| 负控 | 做法 | 结果 |
|---|---|---|
| ① 步骤锁 | 走完 `decompose` 直接跳 `cross_validate` | ✅ 当场拒绝：`跳步违规：当前应走「spawn」却来了「cross_validate」` |
| ② 幽灵单元 | 3 个真文件 + 1 个不存在的 `phantom.txt` 混进单元表 | ✅ 覆盖率 0.75（3/4），`missing=[phantom.txt]`——补扫两轮仍缺，**如实报**，不折叠成绿 |

## 五、触手接线（三个能力位 · domain=security · safe=true）

| 能力位 | 入口 | 只读面 op |
|---|---|---|
| `penetrating_cross_scan` | 全管线 | `status` · `report` · `scan` |
| `hook_enforcer` | 只验钩子（逐单元回"已钩住/未钩住"+指纹一致性） | `status` · `verify` |
| `omission_detector` | 只算覆盖率与遗漏清单（零遗漏唯一裁判） | `status` · `check` |

**接线三处**：注册表（`caps_registry.py`）· 分派（`api.py` 一个共分支三种入口）· 门（**无门**——只读 + 追加留痕；
写面不存在，故不挂 `filesystem_write`；风险面是"读"，与 `tentacle_bind` 的 scan 同类，先例一致）。

**实测（经万能插）**：`cap penetrating_cross_scan` → steps/max_workers 读数；
`cap penetrating_cross_scan '{"op":"scan","target":"registry"}'` → 覆盖 1.0；
`cap omission_detector '{"op":"check","target":"bindings"}'` → **已钩 4349/4349 · 遗漏 0**。

## 六、与其他件的关系（不重叠）

| 件 | 管什么 | 与本案的边界 |
|---|---|---|
| `tentacle_bind`（资产↔触手绑定） | **账**：谁连着谁、断没断 | 本引擎用它的账当**扫描目标之一**（`bindings`），不重复实现绑定 |
| `gbt-security` 的 `sec_*` / 红队内核 | **安全面**（攻击面/漏洞/隐私审计） | 本引擎管**覆盖完整性**（钩子/步骤锁/交叉/遗漏），不判安全结论 |
| `boot-selfcheck` 的判据 | **启动时**验若干不变量 | 本引擎可做它的一条判据（`gaps` 类），但本体是通用扫描器 |
| `trace_store` | 痕迹库存量只读清点 | 本引擎写**自己的**追加式账（`source_kind=cross_scan`），不越权写 trace_store |

## 七、关账判据（本案自己的验收线）

1. **正控**：`registry` 与 `bindings` 覆盖率均 **1.0**、遗漏 0（实测 ✅）；
2. **负控**：跳步被拒 + 幽灵被抓（实测 ✅）；
3. **触手**：三个能力位经万能插可调、读数一致（实测 ✅）；
4. **留痕**：`state/cross_scan_trace.jsonl` 有本轮记录且 `source_kind=cross_scan`（实测 ✅）；
5. **规程**：`gbt-security` 规程点到这三个位（覆盖不破，`verify-distill --domain security` PASS）；
6. **独立复核**：接线三判据（注册表↔分派/账完整性/外部插件）全绿。

## 八、未验账（如实记）

- **并发上限未压测**：默认 8 线程只在 4348 单元量级验过；"亿万级"的调度扩展（分片/分布式）
  **未实现也未验**——本引擎提供的是**可扩展的生成模型**，不是已实现的分布式集群。
- **`tree:<目录>` 目标只在小样本（3 文件 + 1 幽灵）验过**；全仓树（约 1.3 万文件）未跑（会与
  `tentacle_bind coverage` 重复，且 I/O 重）。
- **仲裁路径未在真实分歧上验过**：正控里两路**永远一致**（`arbitrated=0`）——
  要让仲裁真正跑起来得先制造一次"两把尺子量出不同结果"，本轮没造（不为了跑通用例去改真数据）。
- **未接入 cron/自检**：目前靠手动或既有自动化触发；挂进每 6 小时自检环是下一步（等主人点头）。
