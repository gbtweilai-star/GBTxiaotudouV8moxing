  **结论**：给 `%3A` 形状造必然冷的 URL，照样 406 —— **URL 编码 / 形状不是判别量**。
  `%3A` 常 200 只因它是 `urlencode()` 的产物 -> 全世界客户端都在请求这个形状 -> 它在缓存里；
  编码是「热门度」的**代理**。判别量仍是**该 URL 是否命中源侧（Fastly）共享缓存**。

## 23:3x · R-H7：解释器为什么是四个变量里最阴的一个（实证）

风哥判「解释器最阴」——我补三条一手证据，并把结论升级。

### 1 它静默改「依赖解析」（不只是改测试计数）

实测（本仓，同一份代码）：

```
.pylibs 下的 ABI 树        = ['cp314']            ← 只有 cp314 一棵
本解释器 cache_tag         = cpython-314           ← 3.14.5
对应 overlay 存在?          = True                  ← 匹配
激活后 torch 之外的解析：numpy -> 系统 site-packages
                          dxcam -> .pylibs\dxcam
                          cv2   -> .pylibs\cv2
                          py_ecc-> .pylibs\py_ecc
```

而按本仓既有记录：**3.12 下 `.pylibs/cp312` 不存在 ⇒ overlay 不可读 ⇒ 依赖一律由系统 site-packages 提供**。
⇒ **同一个仓库、同一段代码，换解释器就换掉了 `dxcam`/`cv2` 的来源** —— 而这两个正是触手视觉链的核心依赖。
**解释器变量 = 判据执行环境 + 依赖解析结果，两件事一起变，且两边都不吭声。**

### 2 它静默改「谁能启动」

- `py -0p` 列出的本机解释器：**3.13（商店版，默认）· 3.12（C:\Python312）· 3.10（C:\Python310）**；
- `python` 走 PATH 解析到的却是 **install-manager 的 3.14.5**（`AppData\Local\Python\pythoncore-3.14-64`），
  **不在 `py -0p` 名单里** —— 也就是说「本机装了哪几个 Python」这件事本身就有两套答案；
- 而 `C:\Python312\python.exe` 在**我的沙箱身份下起不来**（stdlib 读不到）⇒ 我连基线解释器都无法复现。

### 3 它静默留痕：三代替换堆在同一个 `__pycache__` 里

工作区（排除 `.pylibs`）的 pyc 版本分布：**312 = 84 · 314 = 86 · 310 = 40** ⇒ **三代替换并存**。
本轮之前没人注意，是因为 `.pyc` 不会报错、不会被 git status 标出来、也不进任何记录。
我是**偶然**从 `test_framework.cpython-314.pyc` 的时间戳才发现这次跑的是 3.14。

### 4 结论升级：O61 的红线要加一句

原红线：**跨身份不比对计数，只逐名比对**。
加一句：**跨解释器不但不比对计数，也不比对「依赖来源」** —— 因为 `.pylibs` ABI overlay 会随解释器匹配/不匹配，
`dxcam`/`cv2` 可能一会儿来自 `.pylibs`、一会儿来自系统。
每次回归的四元组记录：**命令 · store 落点 · 身份读数 · 解释器（含 cache_tag）**。

1. **根因彻底闭合**：BitBlt 拒绝访问 = **线程所在桌面不是输入桌面**，而这一步**不是死局**；

| 段 | 吃什么 | 撞的墙 |
|---|---|---|
| ① 读盘 | 磁盘（文件大小） | 65.1 GB 可用（但已含 11.35 GB 页文件） |
| ② 反序列化 | 内存峰值 ≈ 稳态的 1.5–2× | 物理内存 |
| ③ **驻留 + 换页** | **commit limit** | **23.39 GB**（不是物理可用量） |

## 23:5x · R-H19：A 的定义 =「零新增依赖」→ 做成可验（判据 0）

## 23:5x · R-H36：`POST /send` 接口契约（业务拒绝不返 5xx）

风哥第四次提到 `/send`。前三次给的是"**五条要求**"，这次补**可直接实现的契约**（已并入
`gbt_allinone/docs/微信iLink-Bot-评审与改造清单.md §六`）：

```
POST /send       仅回环 + 本地令牌头
Body  to_user（必填/须在白名单内）· text（必填/<=1000 字符）· idempotency_key（必填）
```

| HTTP | 响应 | 含义 |
|---|---|---|
| 200 | `{"ok":true,"delivered":true,"msg_id":"…","duplicate":false}` | 已投递 |
| 200 | `{"ok":true,"duplicate":true}` | **幂等命中**，未重复发（不是错误） |
| 200 | `{"ok":false,"reason_code":"recipient_not_allowed"}` | 白名单外 → 拒发 |
| 200 | `{"ok":false,"reason_code":"text_too_long"}` | 超长 |
| 503 | `{"ok":false,"reason_code":"bot_not_logged_in"}` | 未扫码/凭据失效（**唯一该返 5xx 的**） |
| 401 / 422 | — | 协议层：令牌缺失 / 缺必填字段 |

**核心口径**：**业务性拒绝返 `200 + ok:false + reason_code`，不返 5xx。**
因为 5xx 会**触发上游重试**，而"白名单外/超长"这类拒绝**重试一万次也不会成功** ——
返 5xx 等于把一次拒绝放大成一串重试。只有"凭据失效"这种**重试可能成功**的情形才返 503。

配套：审计只记 `time / to_user / 字数 / duplicate / reason_code`（**正文不入日志**）·
`idempotency_key` 30 分钟内不重发 · **未知 `reason_code` 一律当失败**（fail-closed）。

## 23:5x · R-H37：`POST /webhook` 接口契约（at-least-once + 幂等 + 隐私默认）

风哥第五次提到 webhook。前次给"四个面"，这次补**可直接实现的契约**（并入
`docs/微信iLink-Bot-评审与改造清单.md §七`）：

**请求**：令牌头 + `X-GBT-Delivery-Id`（幂等）+ `X-GBT-Attempt`（观测）；
body 带 `delivery_id / msg_id / from_user / text(可选) / context_token`。

**五种响应下的 Bot 行为**：

| 响应 | Bot 行为 |
|---|---|
| `200 {"ok":true}` | 不再重投 |
| `200 {"ok":true,"duplicate":true}` | 幂等命中，同样**不重投** |
| `200 {"ok":false,"reason_code":"rejected_*"}` | **业务性拒绝：不重投** |
| `401 / 422` | 协议层错误：**不重投**（重投也不会变好），落审计 |
| `5xx / 超时` | **退避重投** 1→2→4→8→16s（上限 5 次），耗尽落队列 |

**三条口径（与 `/send` 同源）**

1. **投递语义是 at-least-once，不是 exactly-once** ⇒ 接收端**必须幂等**；重复投递要返 `ok:true`，
   **返错会被无限重投**。
2. **业务性拒绝返 200，不返 5xx**（同 `/send` 那条）。
3. **失败落盘**：退避耗尽进 `store/` 待投递队列（重启不丢）+ 只读水位（`pending / failed / last_error_code`）。

**一条隐私设计（建议默认开）**：`payload_mode: "signal" | "full"`
—— `signal` 只投 `msg_id / from_user / received_at / 长度`，**不带正文**；`full` 才带，且必须走 `data_export`。
理由：`/webhook` 是唯一会让**私聊正文离开本机**的一环，默认不带 = 把"隐私外泄"从默认行为改成显式选择。
