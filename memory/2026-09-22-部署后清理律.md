# 部署后清理律（Owner 亲授 · 2026-09-22）

> Owner 原话：
> **「要养成一个习惯：在部署之后顺手把旧的清理了，免得搞混了。」**

---

## 一、为什么这条是铁律级的（不是我随手加的）

**它有一个当场发生的证据。**

2026-09-22 晚，Owner 反馈「**颜色还是没变**」。根因不是代码写错，是**旧的东西没清**：

```js
let PKEY='violet';                              // 新默认，改对了
if(localStorage.getItem('capPalette'))          // 但浏览器里还留着旧值
    PKEY = 存储里的值;                           // ← 旧值赢 ⇒ 新默认永远不生效
```

**部署了新版本，却没清掉上一版留下的状态** ⇒
**用户看到的是旧的，而开发者以为已经换新了 —— 两边都蒙在鼓里。**

**这类"搞混"有三个变体，今晚全都出现过：**

| 变体 | 今晚的实例 |
|---|---|
| **残留状态压住新默认** | `capPalette=ochre` 压住新的 `violet` |
| **残留产物当成新的用** | `dist/` 里那个 **5.5 小时前**的 exe，源码早改了 |
| **残留文件当成权威** | `~/GBT-JXDWD` 的 v5 自述，被当成"我是谁" |

**⇒ 三种"搞混"，同一个根因：旧的没清。**

## 二、铁律（写死的口径）

> **每一次部署/发版/改默认，同一次动作里必须把上一版的残留清掉。**
> **清理不是"下次再说"，是部署的一部分 —— 没清 = 这次部署没完。**

### 判据：部署完成的定义

**一次部署算完成，当且仅当下面五条同时成立：**

1. **新版在位** —— 新产物/新代码已落盘且验过
2. **旧版已清** —— 被它取代的那一份已经移除或明确标记为废弃
3. **残留状态已清** —— 缓存、localStorage、临时文件、进程、旧端口占用
4. **引用已更新** —— 指向旧版的地方（入口页、文档、脚本、快捷方式）全部改指新版
5. **有清理记录** —— 清掉了什么、在哪，写进当天的交付说明

**五条缺一，这次部署就是"未完成"** —— 不许说"已经部署好了"。

## 三、每次部署后的清理清单（照做，别凭记忆）

### A. 代码/产物层
- [ ] 被取代的旧版本文件（HTML / exe / 包）—— 移进 `archive/` 或删除
- [ ] 旧构建产物（`dist/` 里过期的那一版）
- [ ] 一次性的临时补丁脚本（改完就该走的那几个 `.py`）
- [ ] `__pycache__` / `.pyc` / 构建缓存

### B. 状态层（最容易漏、最容易"搞混"）
- [ ] **localStorage / sessionStorage 里上一版的键** → **键名带版本号**，或部署时主动清
- [ ] 浏览器缓存（HTML 有强刷需要时，在交付说明里写清 `Ctrl+F5`）
- [ ] 服务端内存里的旧缓存（`_xxx_cache` 这类模块级变量）
- [ ] 旧进程 / 旧端口占用

### C. 引用层
- [ ] 入口页 / 索引页里指向旧版的链接
- [ ] README / 文档里的旧路径
- [ ] 脚本里写死的旧路径（这正是"自我认知失真"那个坑的同型）
- [ ] 快捷方式、桌面图标

### D. 记忆层
- [ ] 旧台账 / 旧清单里已经作废的条目 —— **标记作废，别让下次的我当成事实**

## 四、与既有铁律的关系

| 既有铁律 | 本律补的那一块 |
|---|---|
| **铁律 1 零猜测** | 本律管"**已知的旧东西**"；零猜测管"**未知的东西**" |
| **铁律 2 生产零修改** | 本律是铁律 2 的**收尾动作** —— 晋升完了还要收尾 |
| **铁律 5 疑故障追根因** | 本律防的是"**自己制造的**混因" |
| **铁律 6 严禁假执行** | **部署了却没清 = 一种假执行**：看起来换了新，实际还是旧 |

**⇒ 尤其最后一条：不清旧的部署，在效果上等于没部署。**

## 五、一句话记住它

> **"部署"不是"放上新的"，是"放上新的 + 拿走旧的"。**
> **只做前半句，就是在给下一次的自己埋坑。**
