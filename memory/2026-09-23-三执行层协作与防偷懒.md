## 0. 三条主道各是什么（真身文件，不是概念）

| 层 | 真身 | 它管什么 |
|---|---|---|
| **大脑执行层** | `gbt_allinone/brain_exec.py`（五维 `route`/`execute`/`verify`/`health`/`unify`，每维挂 `@_spanned`）<br>`gbt_allinone/engine.py`（工作流引擎，`_invoke` 调能力） | 指路 → 执行 → 验证 → 自检 → 合一；**每维进出成对落账** |
| **五维合一** | `gbt_allinone/tools/sync_exec.py`（信封 + 四觉 `ear/eye/hand/mouth` + `run()` + **步机制** `step_open`/`step_close`/`run_check`）<br>CLI：`tools/codex-scripts/five-dim.py` | 给"一次有目标的执行"装上**听得清 → 有证据 → 不夸大**的框架 |
| **万能插** | `tools/codex-scripts/omni.py`（人话 → 落点 → 命令 → 要过的门）<br>唯一门：`gbt_allinone/api.py` 的 `run_task` → `_run_task_core` | 让人一句话能落到 158 个能力位 / 本机工具 / 技能上，**默认拒绝**替人乱跑 |

**三条不是并列的三件事**：万能插是**入口**，五维合一是**过程纪律**，大脑是**执行与验证**。
它们共用**同一道门**（`api.run_task`），所以门上的记账就是三者的公共账本。

## 1. 协作链（谁调谁 —— 两条路，都是真的）

**主路（今天真正在跑的）**：

```
人一句话
  └─ omni.ask          语义路由（中文 n-gram × 能力位名/说明/域提示词）→ 给候选 + 可达性
      └─ omni.run      默认拒绝判定（safe ∧ 无参 ∧ 无作用域 ∧ 非侧效应 ∧ 非写动作名）
          └─ five-dim.py cap <kind>            ← 五维合一的 CLI 入口
              ├─ step_open(goal, watch)        → 落 sync_steps.json + sync_ear
              ├─ with envelope():              → 信封（供门记账）
              │   └─ api.run_task → _run_task_core
              │        └─ auto_envelope()      ← 2026-09-23 加的"门口默认同步"
              │        └─ 能力位实现
              └─ step_close(sid, evidence=…)   → 判 ok / partial，落 sync_eye + sync_mouth
```

**真链（五维齐全，今天几乎没人走）**：

```
sync_exec.run(goal)                      ← five-dim.py run / 或直接调用
  └─ with envelope(): _run_inner()
      ├─ ear(goal)                       听不清就中止（sync_abort + ok=False）
      ├─ api.run_task("brain_unify")     走大脑真链
      │   └─ brain_exec.unify → route → execute → verify → health
      │         （每维 @_spanned：brain_enter / brain_exit + 结果契约检查）
      │         └─ engine._invoke → _run_task_core → 能力位
      ├─ eye(watch)                      看现实（哈希对比）；没给 watch 就如实记"这次没看"
      └─ mouth(goal, dims, senses)       总结；**必须报 missed**，否则判 partial
```

**记账分工（这就是"谁干了活"的唯一凭据）**：

| 谁写 | 事件 | 写在哪 |
|---|---|---|
| `api._audit` | `call` / `ok` / `denied` / `user_error` / `error` + `synced` / `synced_via` / `synced_entry` | `store/audit.jsonl` |
| `brain_exec.span` | `brain_enter` / `brain_exit`（带 `dim`），契约不过写 `brain_contract_fail` | 同上 |
| `sync_exec` | `sync_ear` / `sync_eye` / `sync_mouth` / `sync_abort` / `sync_check` | 同上 |
| `sync_exec` | **未收的步**（开着的） | `store/sync_steps.json`（**只存未收步**） |

> ⚠️ 一个容易读错的点（我自己先读错过）：`sync_steps.json` 里 `{}` **不是"没干活"**，
> 是"**当前没有未收的步**"——`step_close` 会 `pop` 掉。步的历史在 `audit.jsonl` 里（带 `step` 字段的那些）。

## 2. 防偷懒机制（**已有**的，逐条给证据形态）

| # | 机制 | 防的是哪种偷懒 | 证据长什么样 |
|---|---|---|---|
| 1 | **唯一门**：一切能力必须过 `run_task` | 绕过授权门直调模块函数 | 账本里 `call` + `auth_denied` |
| 2 | **门口默认同步**（`auto_envelope`） | "谁记得开信封"这种靠纪律的事 | `synced` + `synced_entry=auto` |
| 3 | **归属分格**（`synced_entry`） | 把"默认打开了"冒充"纪律执行得好" | `auto` vs `outer` 分开计数 |
| 4 | **负对照仍可关**（`GBT_ENVELOPE_OFF`） | 尺子变得不可证伪 | `--no-envelope` → `synced=false` |
| 5 | **每维进出成对**（`span` 的 except 分支也落 exit） | 崩一次就永久"卡"着 = 假信号 | `brain_enter` 数 == `brain_exit` 数 |
| 6 | **每维出厂自带结果契约**（`_contract`） | 返回空壳/废话也算"做完了" | `brain_contract_fail` |
| 7 | **`step_close` 不许只报喜** | 改完就说"完成" | 自由文本一律判 `partial`；要 `ok` 得给机检 |
| 8 | **机检必须绑定真执行**（`run_check` + `_FAIL_TOKENS`） | 手打一句 `check:x=pass` 冒充机检 | `sync_check` 记录 + `run_check` 落账 |
| 9 | **嘴必须报 missed** | 只报喜不报忧 | `sync_mouth.missed` |
| 10 | **眼不许默认没问题** | 没看却说"看了" | 不给 `watch` ⇒ `eye.ok=False` |
| 11 | **耳不许空转** | 目标都听不清还瞎干 | 空目标 ⇒ `sync_abort` + 显式 `ok=False` |
| 12 | **全能力位探针**（`cap_probe_all`） | 静默跳过 = "没扫"说成"没问题" | 覆盖必须 **158/158** |
| 13 | **H 维补分母**（`deep_coverage`） | 只报 `checked` 不报跳过 | `checked+skipped+unsafe == 147` |
| 14 | **钉子测试**（`test_sync_exec_nail` 10 条） | 谁删机制谁当场见红 | 缺一维/缺 ok=False/缺 missed 都红 |
| 15 | **默认行为 golden**（`test_api_probe`） | 改坏了没人知道 | 逐字节序列比对 |

## 4. 🔴 偷懒清单（发现的真空档）

### 4.1 【已修·本轮】步账丢步 —— **两条成因，都修了**

- **现象（机检）**：**开步 64 · 收步 49** ⇒ 差 **15 步**；而 `sync_steps.json` 是 `{}`
  ⇒ 这 15 步**既没收、也没留在盘上 —— 是"丢了"**。
- **成因① 落点不跟 store 绑定**（真凶，读代码读到）：
  `_STEPS_FILE = _BASE/'store'/'sync_steps.json'` —— **硬编码仓内 store，无视 `GBT_STORE_DIR`**。
  ⇒ 隔离 store 里跑的 `five-dim.py cap` 会把**开步写进生产步账**，而它的收步落在别处 / 进程被杀
  ⇒ 生产步账上留下**永久孤儿步**。
  **本条是实测出来的**：我用隔离 store 跑并发开步测试时，那 20 步**全部落在生产步账上**
  （随后已清理，清前 20 / 清后 0）。
- **成因② 读-改-写没有锁**：`_steps_load()` → 改 → `_steps_save()` 整文件覆盖，
  两个进程交错就互相覆盖；且 `write_text` 写一半被杀会留**半个 JSON**
  ⇒ 下次解析失败 ⇒ 静默 `{}` ⇒ **所有未收的步一起消失**。
- **危害**：步账是「**欠的活**」的唯一清单。丢了 ⇒ 欠的活看不见 ⇒ 正是偷懒的温床。
- **处置（已做）**：见 §5.1。

### 4.1b 【顺手抓到的第二个真 bug】`sync_exec.run()` 全史只走过 1 次

- `run()`（耳→脑→手→眼→嘴 全链）**全史只有 1 次**（无 `step` 的 `sync_ear/eye/mouth` 各 1 条）。
- 也就是说：**五维合一的"真链"从来没被真正用过**；在用的只是它的一半（开步/收步）。
  这与 §4.2 是同一个病根：**没人把任务交给它**。

### 4.2 【没修·要 Owner 点头】`omni run` 不走大脑、不走五维真链

- **现象**：`omni.py:905` 直接起 `five-dim.py cap <kind>` —— 只到**能力位**这一层。
  `brain_unify` / `sync_exec.run` 的 ear→脑→眼→嘴 **都不参与**。
- **后果**：装钩子后 `brain_unify = 0`、`run() 全链 = 0`。**"三个默认使用"目前只落实了两个**：
  万能插（走门 ✅）+ 五维合一（半步：开步收步 ✅，但没走真链 ❌）+ 大脑（❌）。
- **为什么不擅自改**：`omni run` 的**默认拒绝判定**是安全件；把它插进 `brain_unify`（自己会 route
  再 execute）有可能**绕过那道判定**去执行另一个能力位。这是"安全 vs 到位"的真冲突，
  **要 Owner 定**（方案见 §5.2）。

### 4.3 【已知·设计如此，但要盯着】76% 的步没有硬证据

- 收步 `partial 37 / ok 12`。`partial` 是**如实**（自动收步不编造 `check:`）；
  但它也意味着这些步**证明不了自己干完了**。要往 `ok` 走，必须真跑 `run_check`（`sync_check` 只有 21 次）。

### 4.4 【没查·挂账】`sync_ear` 13 vs `sync_eye` 14（装钩子后）

- 开步数（13）**少于**收步之眼（14），理论上 ear 一定先于 eye。
- 可能是 `cap` 与 `run` 两条路混在同名事件里、也可能是某次异常路径。
  **本轮没查清，如实挂账**（不猜一个解释糊过去）。

## 5. 处置

### 5.1 已做：步账改成**跟 store 绑定 + 加锁 + 原子写**（本轮）

三处改动（`gbt_allinone/tools/sync_exec.py`）：

| # | 改什么 | 防哪个成因 |
|---|---|---|
| 1 | `_STEPS_FILE` 改由 `_paths.STORE_DIR` 解析（**与 store 绑定单一来源**） | 成因① 污染/孤儿步 |
| 2 | 新增 `_steps_lock()`：`O_CREAT\|O_EXCL` 跨进程独占，拿不到**如实返回 `busy`**、不写盘 | 成因② 互相覆盖 |
| 3 | `_steps_save()` 改**临时文件 + `os.replace` 原子替换** | 成因② 半个 JSON |

**实测验证（并发 20 进程同时开步）**：

```
并发 20 开步 → 成功 20 · busy 0 · 子进程报错 0
盘上未收步 = 20 ｜ 不变式（成功数 == 盘上数）: True
丢步 = 0   ← 改前是 15
落点在隔离 store: True   ← 改前会写进生产
残留临时件/锁: 无
```

**钉子测试**：`test_sync_exec_nail.StepLedgerTests` 四条 ——
落点跟 store 绑定 · 锁真独占 · 原子写不留半个/无残渣 · 开收一趟必须回到 0。
（该文件现共 **14** 条，全过。）

⚠️ 顺带记一笔：我在验证过程中**自己往生产步账写了 20 条测试垃圾**
（正是成因① 的现场演示），已用原子替换清回 **0**。**测试污染生产，本身就是这条 bug 的样子。**

### 5.2 待 Owner 定：让 `omni run` 也走五维（**三个默认使用**的最后一格）

**方案 A（保守·推荐）**：`omni run` 判定通过后，用
`sync_exec.run(goal, kind=<判定出的 kind>, use_unify=False)` 执行 ——
即**保留 omni 自己的默认拒绝判定**（不交给 `brain_unify` 重新 route），
但让 **耳/眼/嘴 + 开步收步** 真正参与。五维里的 route 不重复做（omni 已经做过路由了）。

**方案 B（彻底）**：`omni run` 直接走 `sync_exec.run(goal)` 让 `brain_unify` 自己 route。
**风险**：`brain_unify` 自己会选能力位并执行，**可能绕过 omni 的默认拒绝判定** ⇒ 需要先给
`brain_unify` 装同一套判定。**在装上之前不许做。**

### 5.3 顺带：把"丢步"变成**看得见**

未收步清单（`sync_steps.json`）现在只被 `step_close` 读。
应让 `ruler` / `five-dim.py status` 也报**悬空步**（有几步开着、开了多久），
否则丢了还是没人知道。

## 7. 诚实边界

1. **本文的"谁在干活"全部来自账本**。账本没记的，本文不替它说"干了"——
   例如"五维合一在真实业务里有没有用"，本文只给"走了几次"，**判它有没有用要人看目标**。
2. **`count_words` 31 次不是业务**：那是 golden 测试的夹具文本。把它算成"业务调用"就是把测试当生产。
3. **§4.4 那条我没查清**，如实挂着；**不许拿"大概是 X"当结论**。
4. **§4.2 是安全 vs 到位的真冲突**，本文不给"已解决"的假象 —— 它现在**没解决**。
