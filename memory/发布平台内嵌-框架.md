> 那就把"其余"定死在这里，不再回头问同一件事。

## 〇、两条硬边界（先写，免得后面绕）

1. **创作者后台要主人的登录会话**。`studio.youtube.com` / QQ音乐人后台都属**他本人的账号面**。
   ⇒ AI **不代持、不代登、不抓 cookie、不存密码**。只能在他**已经登录好的那个浏览器会话**里操作。
   ⇒ **首次登录永远由主人自己完成**，AI 只在其后动手。
2. **上传/发布是"送出去"的动作**，一律**先问主人**。机器自己的口径本来就有一道 `gate_publish`
   （默认拒「发布」，只放行 plan）。这道闸**不动** —— 这正是它存在的理由。

## 一、架构：一张注册表 + 一条触手通道 + 每平台一张镶嵌卡

```
platforms.json（平台注册表）
      │  每个平台：{id, 名, 后台地址, 登录态怎么认, 上传入口怎么找, 回执长什么样}
      ▼
浏览器触手（唯一操作通道）
      · 走能力位 `browser`（原生窗口 / CDP），**不走各平台 API**
      · 为什么不用 API：API 要凭据 + 要过审 + 平台随时改；触手走的是**人能看见的那条路**，
        主人在旁边看着也能复核（同 `feishu_embed` 的先例）
      ▼
镶嵌卡（面板上一张卡 / 一个按钮）
      · 只读面：当前登录态、待发清单、队列、最近回执
      · 动作面：预览 / 投递 / 重试 —— 每个动作**前**弹一次确认，**后**留一条痕
```

## 二、四条红线（照抄 `feishu_embed` 的先例，一条不放松）

1. **平台是副本，本地是源**：成片以本地落盘为准；平台上的状态只作参考，不作真相。
2. **凭据不落明文**：不记密码、不记 cookie、不导出会话文件。登录态只以"能操作"这一事实体现。
3. **不绕验证**：验证码、二次验证、风控页 —— **遇到就停，交给主人**，不做任何"绕过"的尝试。
4. **每次操作留痕**：走唯一门 `run_task`，`source_kind=publish`，落审计账本。

## 三、每条链的"闭环"长什么样（含回执口径）

| 环节 | 谁做 | 判据（不许用"看着像成功"结案） |
|---|---|---|
| 出片 | ComfyUI（真生成帧）+ ffmpeg（真合成） | 成片文件在盘上、字节数 > 0、能播（ffprobe 读时长/分辨率） |
| 登台 | **主人**（首登） | 页面出现"可上传"的入口元素 —— **触手先看再动**，看得到才算登录态成立 |
| 投递 | 触手（走门） | 平台回一个**可回查的 ID/URL**（YouTube 是 videoId；QQ音乐是作品号）—— 这才是回执 |
| 复核 | 触手 | 用那个 ID 回查一次标题/状态，**能看到**才算发布成立 |
| 留痕 | 门 | 审计账本里有对应的 `run_task` 记录 |

## 五、我在这一轮自己拍板的决定（可推翻，但要有理由）

1. **平台无关**：不做"QQ音乐人专用件"，做注册表 —— 加平台=加一行。
2. **通道只用触手**，不用平台 API（理由见 §一）。
3. **首登人工**：这一步不自动化，也不该自动化。
4. **"无限"落在真无限的那一段**：无限出图（本地、零成本、零审核）+ 一键合成；
   **逐帧生成式视频在本机跑不动**（RAM 7.9GB / 无 CUDA）—— 这条不改口径，避免"无限"变成空话。
5. **回执必须可回查**：拿到 videoId / 作品号并回查一次，才算发布成立。
