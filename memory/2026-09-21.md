## 实测判例 · 语音与蓝牙当前的真实可用度（风哥问「实现了吗」）

- 结论：**V5 里两者都只是能力广场里的名字，没有面板、没有交互**。而且不是我不做——底层就缺件。
- **语音（`voice`）**：
  · `status` → `{tts: "win-sapi（可用）", asr: "needs_dependency"}`
  · `tts`（out 写 WAV，不发声）→ **`denied`**：`capability requires human authorization`，
    缺 `filesystem_write` + `audio_output` 两个作用域；**授权门正常工作，AI 无权自授**（这是纪律不是故障）
  · `asr` → `needs_dependency`，缺 `GBT_ASR_BASE_URL / GBT_ASR_API_KEY`
  · ⇒「听→想→说」链条：**说得靠授权、听得靠后端，两条都没通** → **"语音对话"目前不成立**
- **蓝牙（`bluetooth`）**：`status` → `ble_backend: needs_dependency（No module named 'bleak'）`；
  `scan` → 同样缺 `bleak`，提示 `python -m pip install bleak`。经典蓝牙走 win-bluetooth-stack（状态报告可用）。
  `bt_control`（脑层）状态正常，协议库 8 条：Tuya BLE / Xiaomi Mi / HomeKit HAP / HID over GATT /
  Nordic UART (NUS) / Apple Continuity / Battery Service / Device Information。
  · ⇒ **脑是全的、手没接上**：没装 bleak，scan/connect/read/write 四个原语全部不可用。
- **`voice_orchestra`**：`list` → **17 项技能**（Whisper / Qwen3-ASR / VibeVoice-ASR …）。
  但模块 docstring 写着风哥 2026-09-18 拍板：**本机只跑得动 2 项，因此不开 tab**——
  「面板 tab 是给用户看的能力边界」，「出口清单写实际出口，不写规划出口」。这是框架自己的硬规矩。
- 三条解锁路径（都属主人动作，AI 不自授）：① 终端发 `filesystem_write` + `audio_output` 授权 → TTS 可用；
  ② `pip install bleak` → 蓝牙扫描可用；③ 配 `GBT_ASR_BASE_URL / GBT_ASR_API_KEY` → 语音识别可用（语音对话才成立）。

### 🔴 真渲染又揪出一个**影响所有面板**的严重布局 bug
画星图时发现下半圈画不出来。量了一下：

```
#chatBody  display:flex; flex-direction:column; overflow-y:auto; height:956
子项 #0  渲染高 248  内容高 521   ★ 被压扁
子项 #2  渲染高 132  内容高 275   ★ 被压扁
scrollHeight === clientHeight === 956   ← 容器根本不滚动
```
**根因**：列向 flex 的子项默认 `flex-shrink:1` —— 内容比容器高时**不是滚动，而是被压缩**；
再被 `.card{overflow:hidden}` 把压缩后的溢出裁掉 ⇒ **内容被静默切掉**。

**影响面**：修好后量到 `能力广场` 的 scrollHeight 是 **13,062**，而可视区只有 956 ——
**之前它只露出了约 7% 的内容**（140 个能力里绝大部分从没在屏幕上出现过）。
`关系场` 1,426 / 956。修法一行：`.chat-body>*,.god-body>*{flex:0 0 auto}`，并补 `.god-body{overflow-y:auto}`。

这条又一次印证：**stub 校验器查不出这类 bug —— 它只验证字符串，不验证盒子**。
