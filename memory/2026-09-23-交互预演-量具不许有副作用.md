## 二 🔴、自己捅的娄子 ①：探针把布局写成了"八扇窗全在屏幕外"

**怎么发现的**：`I1` 的读数从首跑的 `isVisible false → true` 变成了 `true → true`
—— 说明那扇窗**启动时就是可见的**。追下去：

```
%APPDATA%\Electron\window-layout.json
  godview / eigenflux / h1 / dsh-chat / exec-deck / code-deck / brain / eye
  **全部 x = -20000, y = -20000**（屏幕外）· 其中 godview 与 brain 还 visible:true
```

**根因**：`startup.cjs` 里"挪一下窗"那一步会触发 `saveWindowState()`，
而它写的是 `app.getPath("userData")/window-layout.json` —— **真那一份**；
`interact.cjs` 点芯片触发 `show()` 也会把 `visible:true` 写进去。**两个探针都在写主人的状态。**

### 但**不能夸大**：核实之后，那份文件**不是真 App 用的那份**

| 路径 | 现读 |
|---|---|
| `%APPDATA%\gbt-potato-desktop\`（`electron .` 真正的 userData） | **不存在** —— 真 App 从没被 `electron .` 启动过 |
| `%APPDATA%\Electron\`（被污染的那份） | 存在 · 那是**探针自己**的 scratch（探针用 `electron <脚本>` 跑，`app.getName()` = "Electron"） |

⇒ **没伤到 App**。但机制是真的、隐患是真的（哪天有人用脚本方式起壳就撞上）。
已把那份被污染的 scratch **收进回收站**（`_recycle_batch` → `(1, [], 0)`），
`loadLayout` 找不到文件就**回落到 `windows.json` 的默认位置**。

### 修法与钉子

- `startup.cjs` / `interact.cjs` 各自在 require `main.cjs` **之前**
  `app.setPath("userData", <各自独立的临时目录>)` —— **顺序必须在前**，
  因为 `main.cjs` 的 `LAYOUT_FILE` 是**载入时**算的；
- 两器各加一条断言：**跑完复核真文件的事前指纹**，被改了就直接判红
  （`S:nopollute` / `I6`）。

## 三 🔴、自己捅的娄子 ②：固定等待 → 批跑只认出 6 扇窗

批跑时 `interact` 报 `I2/I3 Failed: Object has been destroyed`，
单独跑却全绿 —— 典型的**跨探针互相干扰**。查下去是两件事叠在一起：

1. 两个探针**共用**同一个 `%TEMP%\gbt-w3-probe-userdata` ⇒ 一个写的状态影响另一个；
2. `SETTLE_MS = 3500` 这个**固定等待**在批跑时踩空 ——
   铬是挂在 `did-finish-load` 上的，而带 4 个 IPC 调用的那扇页会晚一拍
   ⇒ 有一跑只认出 **6 扇窗，`godview` 缺**（而 `I1` 恰恰要点它）。

**三处修法**：

| 修 | 为什么 |
|---|---|
| 各自独立的探针 home（`gbt-w3-probe-startup` / `-interact`） | 去掉跨探针状态耦合 |
| **轮询到齐**（不再赌固定秒数，上限 12s，连续两次不再增长即认为齐了） | 载入是异步的，固定等待迟早踩空 |
| 用时**重新解析**句柄（`alive()`），失效就如实报"缺哪扇" | 开场那一刻的句柄可能已失效 —— 而原来的写法直接把 Electron 的 `Object has been destroyed` 抛给读的人 |

**连跑三轮**：`startup 8/0` · `interact 7/0`，**无抖动**。
