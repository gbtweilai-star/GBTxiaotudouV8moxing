## 2. 🔴 硬约束：「不破坏 DSH」的**机械定义**（这条比功能重要）

"不破坏"不能靠"我小心"，要有**可判的边界**：

| # | 边界 | 怎么保证 | 怎么验证 |
|---|---|---|---|
| B1 | **不换 DSH 进程/端口**：3080 归 DSH，桌面壳**只是客户端** | 壳里只放 `loadURL("http://127.0.0.1:3080")`；**不许**在壳里实现/代理对话协议 | 打包前后 `Get-NetTCPConnection -LocalPort 3080` 的 pid 不变；对话页刷新后功能齐 |
| B2 | **不改 DSH 配置**：`~/.dsh/settings.yaml`、presets、skills 根**一律不动** | 壳与面板都不写这些路径 | 打包前后对这几个路径取哈希，**不变** |
| B3 | **不占 DSH 端口**：桌面壳自己的服务只用**8765 之外**的端口 | 壳不新增监听；面板服务沿用 8765 | `listen` 端口清单快照比对 |
| B4 | **DSH 页面必须原样能跑**：嵌入 ≠ 改页面 | 用 `<webview>`/`BrowserView` 原样加载 URL，不注入脚本、不拦请求 | 同一 URL 在普通浏览器与壳里**渲染结果对照截图** |
| B5 | **DSH 升级不被我们拖住** | 壳只依赖 URL + 公开 HTTP，不 import DSH 内部模块 | 壳里 grep 不到对 DSH 源码路径的引用 |

> **判据落点**：`tools/codex-scripts/desktop-shell-guard.py`（待建，见 §7 期 1）
> —— 它把 B1–B5 逐条现算并给出 PASS/FAIL，**任一条 FAIL 就不许打包**。

## 5. 专业级编程AI 的 gap 分析（**先认现有，再谈缺**）

**已经有的（37 条能力位 + 现成工具）**：

| 面 | 现有 | 状态 |
|---|---|---|
| 模型通道 | `llm_chat` / `llm_status` / `local_brain` / `model_key_pool` | 只读契约面在；`keys_total=0`（没配密钥池） |
| 外部编程桥 | `codex_status` / `codex_tools` / `codex_models` / `codex_chat` / `codex_thread_new` / `codex_turn_send` / `codex_interrupt` | **7 条真桥接**（走 codex，有真 handler） |
| 项目上下文 | `project_context` / `context_vault` / `brain_vault` | `project_context` 真跑；`context_vault` 是骨架 |
| 提示词 | `prompt_bridge`（compile/passthrough/status） | 真跑（有测试） |
| 代码体检 | `cross_scan` / `selfscan` / `truth_scan` / `root_fix` / `caps_called_audit` + `quick_scan` / `audit_code_taste.py` | 工具全在、真跑 |
| 工程纪律 | `framework_gate` / `regression_stamp` / `signature_guard` / `file_hygiene` | 真跑 |
| 版本控制 | **无 `git_*` 能力位**（只有 `git` 命令行 + 扫描器里的 git 读数） | **缺** |
| 多文件编辑/补丁 | **无 `patch` / `edit` 能力位**（改文件靠 agent 工具 + `safe_io`） | **缺（设计缺口）** |
| 测试运行 | `regression_stamp`（四元组印章）+ pytest | 有，但**不在能力位里** |
| LSP/符号索引 | **无** | **缺** |
| 终端 | `tentacle` 系列（桌面操控）+ `shell` 服务（DSH 侧） | 部分 |

**结论（专业级的三个真缺口）**：

1. **"改代码"不在能力面里**：现在改文件走的是 **agent 工具**（`edit`/`write`），不经过 `run_task` 那道门
   ⇒ 没有审计、没有信封、没有步账。**专业级编程AI 的第一件事**：把"改代码"做成**过门的能力**
   （`code_patch`：dry-run + 逐字节 before/after 哈希 + 门 + 回执），而不是继续让 agent 直接写盘。
2. **没有"项目级上下文"能力**：`project_context` 太薄；专业级要**符号/依赖/调用图/测试面**四件，
   现成零件有（`call_graph` 测试、`code_exhaustive_scan`、`deps` 读数）但**没合成一个能力位**。
3. **没有版本控制能力位**：`git_*` 全缺，而本仓 13.4 万次调用已经证明"改完要能回滚"是刚需。

### 6.1 `omni run` 走五维默认路径（三执行层「默认使用」的最后一格）

- **改前**：`omni.py` 直接起 `five-dim.py cap` ⇒ 只到能力位那层；机检：装钩子后 `brain_unify=0`、`run() 全链=0`。

## 6.4 【round 2】窗 A 的第一块砖 + 一个**硬约束**浮出来

### 挖到的硬约束：对话面**不是裸 URL 就能嵌的**

```
GET http://127.0.0.1:3080/   →   HTTP 401
body 原文：dsh web authentication required; reopen the URL printed by dsh web.
```

⇒ DSH 的 web 面用的是 **`dsh web` 启动时打印的那条带 token 的 URL**。
**裸 URL 一定 401**，所以"把对话面嵌进壳"这件事**不是 `loadURL` 就完事**。

**本仓的纪律直接决定了处置**：凭据**不许明文落盘** ⇒
**注册表不写 token、不写 URL**，壳也**不替主人去翻凭据**。
⇒ 于是有了 `needs_url` 这条声明：窗 A 只声明"它需要一条主人给的 URL"，打开的是**本地引导页**。

### 本轮落地（都只做加法，DSH 一个字节没动）

| # | 改什么 | 为什么这么做 |
|---|---|---|
| 1 | `main.cjs`：`createWindow` 支持 `entry.url` → `loadURL`，**但过 `loopbackUrlOnly()` 白名单**（只放行 127.0.0.1 / localhost / ::1） | `loadURL` 不限域 = 这个常驻托盘壳变成**通用浏览器**，是完全不同的安全面。拒绝时**写清楚原因**并落到 `blocked.html`，不静默 |
| 2 | `main.cjs`：`entry.needs_url` → 载入本地 `connect.html` | 需要主人运行时给 URL 的窗，注册表里**只声明需求**，不存凭据 |
| 3 | `windows.json`：登记 **窗 A `dsh-chat`**（`needs_url: true` · `port: 3080` · `visible: false`） | 默认不开（《宿主不打扰律》）；并把 401 实测与"不写 token"的规矩**写进注册表本身**，免得后人重踩 |
| 4 | 新增 `holo_pet_w3/shell/connect.html` | 引导页：说清 401 原文 + 三步做法 + **明确不做"自动找 token"**（那等于替你翻凭据） |
| 5 | 守卫加 **B1d**（对话面可达性：200=PASS / 401=PENDING / 其它=FAIL）与 **B6**（URL 白名单：注册表里出现非回环 url 即 FAIL） | 把"嵌不了"和"可能变通用浏览器"两件事都变成**看得见的格子** |
| 6 | 守卫退出码分三档：**0=全过可打包 · 1=有破坏不许打包 · 2=还没做完** | 只有两档时，"还没做"会被读成"没问题"。开发期可用 `--allow-pending` 取 0，**打包前不许加** |

### P1 的验收口径随之修正

## 6.7 【round 5】P2 第一缺口：**「改代码」从此过门**（`code_patch`）

### 缺口是什么

在此之前 **改代码不过门**：agent 直接 `edit` / `write` 落盘 ——
**没有审计、没有信封、没有步账、没有"改前改后"凭据**。
而"专业级编程AI"的第一块地基就是：**每一次改动都能自证**。

### 落地：`gbt_allinone/tools/code_patch.py` + 能力位登记

| 面 | 内容 |
|---|---|
| 三原语 | `dry_run`（**默认，只算不写**）· `apply`（落盘）· `rollback`（按回执退回） |
| 九道机械闸 | **仓内**（解析后必须在仓内）· **find 恰好一次**（0 ⇒ `not_found`；>1 ⇒ `ambiguous`，**绝不替你挑一个**）· **空改动拒写** · `expect_sha256` 对不上拒 · **二进制拒改**（前 8KB 有 NUL）· >4MB 拒改 · **逐字节替换**（CRLF/BOM 一个字节不动）· **原子写**（tmp+`os.replace`）· **回执可回滚** |
| 回执 | 记 `find`/`replace`/改前改后哈希 —— **不写整份文件**；回滚前先核 `after_sha256`，**对不上就拒**（文件被人动过，不猜） |
| 门 | `dry_run` **零作用域**；`apply`/`rollback` 挂 **`filesystem_write`**；**fail-closed** —— 没见过的 op 也照挂 |
| 登记 | `safe: False`（有写面 ⇒ 面板/omni 不许自动代调）；入参契约登记在**能力位自己身上**（见下） |

### 🔴 本轮踩到一个"登记位置"的真问题（值得单独记）

我第一次把 `code_patch` 放进 `PARAM_REQUIRED` —— 全量测试立刻红：
`test_param_required_contract_has_evidence` 第 456 行的规矩是
**`PARAM_REQUIRED` 只收 `safe: True` 的能力位**（那是"给面板代调用"的入参契约表）。

**两条路不能走**：① 把写盘能力标 `safe: True`（为了让测试变绿而放宽安全面 —— 绝不）；
② 干脆不登记参数（`all_caps()` 会读成 `requires_params: False` —— **假读数**："不用参数也能跑"）。

**走的是第三条**：契约登记在**能力位自己的条目上**（`requires_params`/`params`/`params_hint`），
由 `all_caps()` 与 `required_params()`/`params_hint()` 一并带出。
⇒ 契约不丢（实测 `requires_params=True, params=['path','find','replace']`），
也**没有**把写盘能力混进面板可代调名单。

### 端到端实测（走五维/万能插 CLI）

```
① 默认档（dry_run）：status=ok · wrote=false · occurrences=1 · before/after_sha256 都有 · 文件没变
② op=apply：status=**denied** · reason="需要人工授权（filesystem_write）" · missing_scopes 有值
③ 拦下之后：文件内容一字未变
```

⇒ **缺口堵上了**：改代码要过门；未授权时**拒得清楚**（说得出缺哪个作用域）。

## 6.8 【round 6】P2 第二缺口：**版本库能力位**（`git_read` / `git_write`）

### 为什么**拆成两件**，不合成一个带 `op` 的大件

`safe` 是按**能力位**记的，不是按 op 记的。合成一件就必须回答"它到底 safe 不 safe"，
而正确答案是"看 op"—— 那正是含糊的来源。拆开之后门的判据**平凡正确**：

| 能力位 | safe | 作用域 | op |
|---|---|---|---|
| `git_read` | **True** | **永远零作用域**（policy 里显式空挂，让"零作用域"是一条看得见的决定） | status / diff / log / show / branch_list / stash_list |
| `git_write` | **False** | **永远挂 `filesystem_write`**（连它不认识的 op 也挂 —— fail-closed） | stage / commit（**必须点名 paths**） |

### 七道机械闸

**绝不过 shell**（一律 `shell=False`）· **反选项注入**（`rev`/`path`/`message` 不许以 `-` 开头
—— 经典 `--upload-pack=…` 就是这么塞进去的）· **路径必须在仓内** · **每条命令带 `--`** ·
**超时 60s + 输出上限 200KB** · status 只报数量与前 40 条（本仓脏行上万）· **写面必须点名路径**
（`commit -a` 一次就把不相干的全卷进去）；`commit` 用 **pathspec-limited**（`git commit -m … -- <paths>`）。

**如实不做**：`reset` / `rebase` / `push` / `--force` —— 那是"改历史/出网"，要单独设计。
测试里有静态钉子**不许这些字样出现**（防止悄悄长出来）。

### 🔴 本轮抓到框架一处**读数自相矛盾**（比新能力更值钱）

我第一版在 api 的 dispatch 里 **catch 异常、返回错误 dict**。框架把"返回了 dict"读成
"执行成功，结果在里面"，于是外层是：

```
{"status": "ok", ... "result": {"ok": false, "reason_code": "option_injection"}}
         ↑ 外面 ok，里面说拒了
```

**框架的约定其实是"用法/参数类错误要抛"**：`api._run_task_core` 有一支
`except (ValueError, TypeError, KeyError, EngineError, …)` ⇒ 收敛成
`status: error` + `error_class: user_error` 并记 `user_error` 审计。
⇒ 修法两条：① `CodePatchError` / `GitRepoError` **继承 `ValueError`**，并且**不吞**；
② 在那一支里**通用加上 `reason_code` 透传**（`getattr(e, "code", None)`）——
任何 raise 出带 `.code` 的 ValueError 的能力都受益，不是给这两件开特例。

修后实测：注入 / 没找到 / 空改动 ⇒ `status=error · error_class=user_error · reason_code=…`；
门拦仍是 `status=denied · missing=['filesystem_write']`。**两件事不再混在一格里。**
