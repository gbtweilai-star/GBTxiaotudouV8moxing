🎯 一、审计目标（先对齐）

1. 盘点现有能力

这个框架"已经能稳定产出什么"

2. 识别未实现能力

技术上可实现但当前缺失/半成品

3. 判断生产可用性

是否可上线、可回归、可观测、可扩展

4. 输出落地计划

按优先级给出"先补什么、怎么补、补到什么验收标准"

📐 二、审计维度（全框架，不漏项）

1. 能力域

  • 已实现功能清单（用户可见能力）
  • 隐式能力（脚本、任务链、自动化流程）
  • 能力边界（做不到什么）

2. 流程编排域

  • 主流程、分流、回退机制
  • 异常分支（超时/失败/重试/降级）
  • 任务状态机是否闭环

3. 模型与推理域

  • Prompt/规则加载链是否可控
  • 工具调用成功率、重试策略、幂等
  • 上下文注入与记忆机制有效性

4. 工程质量域

  • 模块边界、耦合度、重复逻辑
  • 配置管理、环境隔离、密钥治理
  • 静态检查、类型约束、lint/test 覆盖

5. 数据与状态域

  • 输入输出 schema 是否稳定
  • 缓存、会话、持久化一致性
  • 数据迁移与回滚机制

6. 可观测性域

  • 日志结构化程度
  • 指标（成功率/延迟/成本/错误类型）
  • Trace（一次任务全链路可追踪）

7. 发布与运维域

  • CI/CD 完整性、环境一致性
  • 灰度/回滚/热修复能力
  • 依赖与供应链安全（SCA）

8. 性能与容量域

  • 峰值并发能力
  • 冷启动与关键链路时延
  • 大输入（长文档/多文件）稳定性

9. 安全与合规域

  • 权限最小化、Token 生命周期
  • 输入注入/越权/路径穿越等风险
  • 隐私数据脱敏与日志泄露控制

10. 产品化域

  • 组件复用、页面模板化、资源构建链、错误边界
  • 服务入口、任务编排、异常处理、配置/密钥加载
  • API 契约、错误码规范、超时重试、降级策略
🔄 三、审计方法（四步闭环）
Step 1：资产清点（Inventory）
半天

代码目录、配置、脚本、Actions、文档、规则文件、技能文件 → 输出《能力清单 v0》

Step 2：证据采集（Evidence）
半天

静态证据（代码、配置、工作流、测试）+ 动态证据（运行日志、Actions 失败记录、时延/错误分布）→ 结果必须"有证据链接/文件路径"

Step 3：能力评级（Scoring）
1 天

每个能力按 0–5 分评级：

  • 0 不存在
  • 1 概念验证
  • 2 可运行但不稳定
  • 3 稳定可用（基础生产）
  • 4 可规模化（监控/回滚齐全）
  • 5 最佳实践（自动化完备）
Step 4：改造路线图（Roadmap）
1 天

按优先级分三层：

  • P0（立即） 影响可用性/安全/数据正确性
  • P1（短期） 影响效率和规模化
  • P2（中期） 体验优化与架构演进
🔍 四、重点：如何定义"技术上能做到但没实现"

1. 有明确实现路径

已有依赖或可引入成熟方案

2. 改造成本可控

人天可估，非科研级不确定性

3. 收益可量化

成功率、时延、错误率、维护成本

⚡ 七、优先审计建议（HTML/Python 混合项目）

1. 前端生产能力

组件复用、页面模板化、资源构建链、错误边界

2. Python 侧能力

服务入口、任务编排、异常处理、配置/密钥加载

3. 前后联动

API 契约、错误码规范、超时重试、降级策略

4. CI/CD 与质量门禁

lint/test/build/release 是否强制门禁

5. 运行可观测

失败定位是否能在 5 分钟内完成
