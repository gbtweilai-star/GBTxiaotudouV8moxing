## 一、跨文件调用图（从 `DeusData/codebase-memory-mcp` 蒸馏）

### 1.1 为什么**不安装**它（三条硬理由，都是实测）

| # | 理由 | 证据 |
|---|---|---|
| 1 | **它自己写明会改写 agent 配置文件** | README 原文：*"This tool reads your codebase and **writes to your agent configuration files**. That is what it is designed to do."* 而本机 `.claude`/`.codex`/`.gemini`/`.agents` **四个目录都在** ⇒ 它会真去写我们的指令面 |
| 2 | **它给 Claude Code 装 PreToolUse 钩子拦截 Grep/Glob** | README 原文；那是**插进我们工具链** |
| 3 | **本机一个 C/C++ 编译器都没有** | 实测 `gcc`/`clang`/`cl`/`make`/`cmake`/`zig`/`tcc` **全无**，它是纯 C 单二进制 ⇒ 源码构建不可行，只剩下预编译二进制 |

**另外量到**：仓 169 MB；上游 MIT。

### 1.2 蒸馏了什么 → `gbt_allinone/tools/call_graph.py`（零依赖，纯 stdlib AST + SQLite）

| 它的东西 | 我们这里 |
|---|---|
| 节点 `Module/Class/Function/Method` | `模块::类.方法` 限定名 |
| 边 `IMPORTS` | `import a.b` / `import a.b as m` / `from X import y` / 相对导入 |
| 边 `CALLS`（import-aware） | 裸名 / `self.m()` / 模块别名 / 点号链；**解析不出就如实说为什么** |
| `trace_path`（BFS 谁调用我/我调用谁） | `trace(name, depth, direction)`，**每跳带 raw 原文**供核对 |
| 死代码检测 | `dead_code()`，**分三桶**（见下） |
| `detect_changes`（git diff → 受影响符号） | `impact(paths)` 反向可达 |
| 持久化 SQLite 图 | `store/call_graph.sqlite3`，边带 `via` 列标明**靠哪一遍认下的** |

### 1.3 我们比它多做的三道闸（都是实测逼出来的）

**闸 1 · 死代码分三桶，不把"解析不出来"说成"没人用"**

它只看 AST 零调用者。**在我们仓里这会误杀**：我们大量**按名派单**
（`caps_registry.py` 的 `"handler": "browser"`、`_READ_ONLY_TENTACLE` 名字集合、`getattr(t, name)`）。
所以分三桶：

- `dead`：无调用者 **且** 名字不在任何字符串里 **且** 没被当值引用 ⇒ 才敢说死
- `suspect`：名字出现在**字符串**里 ⇒ 可能按名派单，**要人看**
- `as_value`：被**当值引用**过（`app.on("run", on_run)`、装饰器、partial）⇒ **在用，不是死**

实测效果：`dead` 从 233 → **145**（`as_value` 桶收走 75 个回调）。

**闸 2 · 悬空边自查（这条抓到了最大的一个 bug）**

`stats()` 会算 **`dangling_edges`＝callee 不在符号表里的边**。
首轮实测 **6,217 条**，样例如 `codex_bridge::CodexAppServer._pending.clear` ——
`self._pending.clear()` 被我的 `self.X()` 规则整个当成方法名。
根因：**触手是 9 个 mixin 合成的**，`OmniDomainMixin` 里写 `self.find_text()` 而
`find_text` 定义在 `OmniReadMixin` 上；我只在所在类里找，找不到就**凭空编了个限定名**。

**铁律（已写进代码注释）：解析器永远不许返回一个不存在的限定名。**
修完 `dangling_edges = 0` —— 这是**构造上成立**的，不是碰巧。

**闸 3 · 两类边分开报**

`calls_import_aware`（明确导入绑定）与 `calls_by_unique_name`（**全仓同名且唯一**，多解一律不认、
内建名不认）**分开计数**，永远看得见哪批是靠唯一性认的。第二遍多认下 **10,688** 条。

### 1.4 真仓读数（诚实口径）

```
files=328  unparsed=0  symbols=5298
calls_import_aware   =  5507
calls_by_unique_name = 10688
calls_unresolved     = 31581
unresolved_ratio     = 0.661      ← 两遍之后仍解析不出 66%
dangling_edges       = 0          ← 铁律成立
imports = 2335   strings = 24928
```

> 🔴 **`unresolved_ratio = 0.661` 是这张图最重要的数字，不许藏。**
> 它比修 bug 之前**更高**（0.611 → 0.661）—— 因为我把**编出来的假边**换成了如实承认。
> 报告里对此有硬告警：**"这张图不完整，`dead_code` 的结论要打折看"**。
> 剩下解析不出的，绝大多数是"对象属性上的方法"（AST 拿不到类型）与 stdlib 基类方法 —— 本来就追不到。

**跨文件确实通了**：修完后 `OmniReadMixin.find_text` 的调用者列出来 **7 个，
横跨 `omni_domain`/`omni_keyboard`/`omni_mouse`/`omni_read`/`omni_window` 5 个 mixin 文件** —— 此前全是断的。

### 1.5 用例：`gbt_allinone/tests/test_call_graph.py` — **10/10 通过**

含四条不许越的线：跨文件 import 解析 · **多解不认** · **内建名不认** · 死代码三桶。
另有一条反向用例：**同模块内 `def len` 之后 `len()` 就是调它自己**（Python 语义如此，遮蔽是对的）。

> 写这条时我自己先写错了一个断言（以为"内建永不被认"）——**是测试逼我把语义想清楚的**，
> 最后拆成"别处同名不许认"+ "本模块遮蔽该认"两条。

## 二、第 10 域「听与说」（从 `xinnan-tech/xiaozhi-esp32-server` 蒸馏）

### 2.1 它是什么

`paysssk-creator/xiaozhi-esp32-server` = fork 自 `xinnan-tech/xiaozhi-esp32-server`
（**10,657 stars**，**MIT**，191 MB，华南理工大学刘思源教授团队主导）——
**ESP32 语音设备的后端**，核心是一条完整实时语音流水线：

**VAD（SileroVAD）→ ASR（FunASR/SherpaASR）→ LLM → TTS（EdgeTTS）** + **声纹识别（3D-Speaker）** + 流式 + 实时打断。

⚠️ 它自己的警告照录：**「本项目功能未完善，且未通过网络安全测评，请勿在生产环境中使用」**。

### 2.2 为什么它对我们价值极高

**它精准命中我们实测出来的缺口**：本仓 `TENTACLE_MANIFEST` 以前对大脑宣称
「👂 听觉: WASAPI回环」，而触手当时 **8 个域 105 个方法里一个音频方法都没有** —— 那条假声称同日被我改成真话。
本域就是把这块补上。

### 2.3 落法：**按本机实测决定**，不照抄它的依赖

| 依赖 | 本机 | 影响 |
|---|---|---|
| `torch` / `numpy` / `scipy` | **有** | VAD 可行 |
| **`sounddevice`/`pyaudio`/`soundcard`** | **全无** | 🔴 没有音频 I/O 库（真正卡点） |
| `onnxruntime` / `funasr` / `sherpa_onnx` | 无 | SileroVAD 与流式 ASR 不可用 |
| **`win32com` + `comtypes`** | **都有** | 🌟 **Windows SAPI 可用 ⇒ 说话零新依赖** |
| `winsound`（stdlib） | 有 | 播放 WAV / 蜂鸣 |
| `audioop` | 无（3.13 起移除） | PCM 处理自己做 |

### 2.4 落成 `gbt_allinone/tentacle/omni_audio.py`（9 个方法，零新依赖）

| 环节 | 我们这里 | 实测状态 |
|---|---|---|
| 说话 | `audio_speak`（SAPI）/ `audio_voices` | ✅ **实测 3 个发音人**：Huihui 中文 / Zira / David |
| 播放 | `audio_play_wav` / `audio_beep` / `audio_stop` | ✅ winsound（stdlib） |
| 设备 | `audio_devices`（ctypes+winmm） | ✅ **实测读出 `扬声器 (Realtek(R) Audio)`，2 声道**；**录音设备 = 0** |
| 基础件 | `audio_wav_info`（WAV 头）/ `audio_vad_energy`（轻量 VAD） | ✅ 实测：440Hz/1s → 16000Hz/1.0s；VAD 前半静音不触发、后半 17/33 帧有声 |
| **采集** | `audio_record` | ❌ **未落地**。本机 `waveInGetNumDevs = 0`（真的没有麦克风）。**如实返回失败，绝不产出假音频** |

**过程中修掉一个真 bug**：`WAVEOUTCAPSW` 结构体我漏了最后的 `dwSupport` 字段 ⇒ `sizeof` 不对 ⇒
`waveOutGetDevCapsW` 直接返回 **11（MMSYSERR_INVALPARAM）**，设备枚举全废。补回来才读出扬声器。

### 2.5 仍然缺的（已写进 MANIFEST，遇到就说做不到）

- ❌ **采集**（`audio_record` 未落地；本机无麦克风设备）
- ❌ **WASAPI 回环**（听电脑在放什么）—— **"听觉"最要紧的那半，仍然缺**
- ❌ **流式 ASR/TTS 与实时打断（barge-in）**
- ❌ **声纹识别**（分不清是谁在说）
- ⚠️ `audio_vad_energy` **不是 SileroVAD**，是零依赖轻量替身（能量+过零率），噪声环境误判率高

### 2.6 用例：`gbt_allinone/tests/test_omni_audio.py` — **10/10 通过**

四条诚实性断言：设备读不到就如实说 · 非 WAV 明确拒绝 · **VAD 判定必须跟信号对上** ·
**采集做不到就必须失败且不留任何音频文件**（这条是防"假音频"的硬闸）。

**本轮自己抓到自己 3 个错**（都写进了代码注释，防再犯）：
① `visit_Import` 把 `import a.b` 与 `import a.b as m` 混为一谈 ⇒ `pkg.a.alpha()` 拼成 `pkg.a.a.alpha`；
② `self.X.Y()` 当成方法名 ⇒ 6,217 条悬空边；
③ `WAVEOUTCAPSW` 漏 `dwSupport` ⇒ winmm 返回 11。
**三个都是"跑出来/量出来"才发现的，不是想出来的。**
