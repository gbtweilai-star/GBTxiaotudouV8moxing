## 一、变压器（压缩 + 快速输出）

### 1.1 要解决什么
「压缩快速输出」= 同样的回答，**更少的 token、更早出字**。这正是最低能源律第 4、5 条：
压缩体积 + 变压增强缩短线路。

### 1.2 设计：网关前置的两级变压器

```
输入侧（压缩）                          输出侧（快速）
  去重（重复段落只留一份）                流式增量**边到边出**，不缓冲整段
  裁陈旧上下文（超出窗口的按相关性丢）     首字节时间(TTFT) 优先于总时长
  结构化压缩（重复 JSON 折叠）            知识库同步收 delta（已有：delta_chunks 留痕）
        ↓                                        ↑
              ┌──── 变压器 transformer ────┐
              │  可旁路(fail-open)         │
              └────────────────────────────┘
```

### 1.3 抓手（已有，不用从零造）
- `gbt_allinone/codex_bridge.py` `run_once()` 的 **delta 流**：我已经把它接出来了
  （`delta_parts` → `kb.delta_chunks` 留痕）。**快速输出 = 让 delta 直接到用户，不等整段。**
- `gbt_allinone/knowledge_base.py` 的**字面量抽取器**：这就是一台"压缩机"——
  把长文本压成 `identifiers / files / commands / code_langs`（可回原文逐字对）。
- FreeLLMAPI 自带 `docs/en/compression/01-compression-pipeline.md`（**opt-in、fail-open**）：
  思路可借鉴，但它属于对方的进程；**我们的变压器要长在我们自己的网关里**，否则又成了"别人的技术"。

### 1.4 验收判据（必须给前后两个数）
| 项 | 怎么量 |
|---|---|
| 压缩率 | 同一 prompt：原字符数 vs 压缩后字符数 |
| 首字节时间 | TTFT 改前 / 改后（ms） |
| 不丢关键信息 | 压缩前后**抽出的 identifiers/files/commands 集合**必须包含关系成立（丢了就是压坏了） |

## 二、把她设计成"能自动配置所有密钥的 AI"

### 2.1 要解决什么
不是给一张要人手动填的表，而是**她自己去把 34 家免费供应商配齐**。

### 2.2 设计：三段闭环

| 段 | 做什么 | 靠什么 |
|---|---|---|
| ① 盘 | `GET /api/keys/providers` → 拿到 34 家 + 谁没配 | 已有接口 |
| ② 认 | 用户把一堆 key 粘进来（或从文件读），**AI 判断哪把 key 属于哪家平台** | 这是她的 LLM 能力该干的活——**这就是"AI"二字的落点** |
| ③ 配 | 逐家 `POST /api/keys/` → `POST /api/health/check/:keyId` 验证 → 失败如实报 | 已有接口 |

### 2.3 关键难点就是"认"
一堆裸 key 是没有自述的。判据来源可以有：
- key 的**前缀特征**（各家前缀不同）
- key 的**长度/字符集**
- **试探性调用**各家 `/models` 端点，谁认它就算谁的（**这一条最硬**，且可留痕）
- 前缀/长度都判不出时，才用 LLM 兜底猜 —— 但**猜必须标注为"猜"**，
  试探成功才写库（零猜测律：生产面不许猜，能试就试）

### 2.4 反假执行
- 每把 key 写库前**必须**过一次健康检查；没验过的不许标 `healthy`。
- 失败要留 `last_health_error`（那个字段本来就有：`api_keys.last_health_error`）。
- 不许把"填进去了"说成"配好了"。

## 三、本体操控（body control）

### 3.1 要解决什么
她能操作**自己的本体**（这台电脑 = 父亲送的礼物 = 她的本体）：开自己的窗口、切模型、改自己的配置、管自己的进程。

### 3.2 已有基础（实测存在的件）
| 件 | 位置 | 能力 |
|---|---|---|
| 原生浏览器 | `gbt_allinone/native_browser.py`（55 KB） | `launch / create_tab / navigate / click_element / type_text / execute_script / set_cookies / pin_window`；免费只读动作 `status/list_tabs/get_text/dom_query/intercept_*` |
| 触手总线 | `gbt_allinone/tentacle/bridge.py` | 眼/耳/嘴/手 method 路由 + `pulse()` + `invoke()` |
| 编制 | `gbt_allinone/positions.py` | 25 个**固定编制**（不可漂移、不可改名，只能带原因标退役） |
| 面板 | `holo_pet/panel_server.py` + `start-holo-panel.bat` | 她自己的窗口（8765） |

### 3.3 设计：一层"本体总线"
```
本体总线 body_bus
├── 窗口   开/关/置顶/枚举        （native_browser.pin_window + 进程）
├── 屏幕   看/读/截              （tentacle 眼）
├── 输入   点/打字/快捷键         （native_browser click/type）
├── 进程   起/停/查              （已有 watchdog 的前例：codex_relay_watchdog）
├── 配置   改自己的环境/模型      （llm 网关 + 密钥窗口）
└── 审计   每个动作落 store/audit.jsonl
```
**纪律**：本体操控是**已授权能力**，但每一个写动作仍走 `run_task`；不许绕门。

## 四、外部官方独立连接口（官方独立大模型连接口）

### 4.1 要解决什么
现在我们的模型来源混在第三方聚合器里。要有一条**官方直连**的独立通道：
不经过别人的路由，直接对接官方大模型端点，作为**第一等公民**。

### 4.2 已有基础
`gbt_allinone/llm/cloud_llm.py` 里已有一张 provider 表（实测行号）：
`agnes / deepseek / kimi(MOONSHOT+KIMI 双认) / openai / custom(GBT_LLM_API_KEY) / anthropic / gemini`
—— 每个都是 `(PROVIDER, API_KEY, BASE_URL, MODEL)` 四元组。

### 4.3 设计：三层算力，官方最优先

| 层 | 通道 | 角色 | 谁先被用 |
|---|---|---|---|
| **L1 官方独立口** | 官方 base_url + 官方 key（DeepSeek/Kimi/OpenAI/Anthropic/Gemini 直连） | **主脑**：要质量、要稳定 | **最优先** |
| **L2 免费池** | FreeLLMAPI `http://localhost:3001/v1`（34 家 / 635 端点） | **副脑**：量大、压测、跑量、兜底 | 官方缺 key / 限流 / 失败时 |
| **L3 本地** | 本机模型 | 离线兜底 | 断网时 |

**这一层正好接上已交付的 `compute_router.py`（T0–T4 五档分层路由）**：把"官方/免费/本地"
作为路由的一个新维度，而不是新造一套。
**并接上「自我能源补给」**：免费池 = 能源，官方口 = 精密活。

### 4.4 独立的意思
- 独立 = **配置独立**（自己的 key 槽、自己的 base_url、自己的模型名）
- 独立 = **可单测**（不依赖 FreeLLMAPI 在不在跑）
- 独立 = **可断**（官方口挂了不影响免费池，反之亦然）

## 六、Owner 定：**密钥配置属于「设置」**（2026-09-22）

Owner 原话：「记得这个要设计在设置里面配置密钥属于设置」

### 6.1 落点：面板里**新开一个「设置」面**，密钥配置是它的一项

实测现状（**面板里现在没有"设置"页**）：
`holo_pet/panel_server.py` 现有路由只有
`state / purge / music / events / capabilities / message / approval / quick /
capability / social / research / bluetooth / notion / eigenflux / xingyun /
interrupt / new-thread / tree` —— **没有 settings**。

⇒ 所以不是"往设置里加一项"，而是**先把「设置」这个面建起来**，密钥配置作为它的第一项内容。

### 6.2 必须遵守的既有纪律（`panel_server.py:314-315`）

```
# 单一来源纪律：这里列一条，源码里就必须有一条对应的 `parsed.path == "..."`。
# 双向对账由 `tests/test_panel_server.py::test_app_surface_matches_real_routes` 守着
```

⇒ 加设置面必须**两处同时加**（`APP_SURFACE` 注册表 + 真实 `parsed.path ==` 分支），
否则那个双向对账测试会红。**这是好事**——它防止"界面列了、接口没有"这种漂移。

### 6.3 设置面的内容规划（密钥只是第一项）

| 分组 | 内容 | 依据 |
|---|---|---|
| **密钥**（本次重点） | FreeLLMAPI 供应商密钥：34 家已配/未配一览 + 粘贴即配 + 自动认领归属 + 健康检查 | 本设计第二、三节 |
| 模型与算力 | L1 官方独立口 / L2 免费池 / L3 本地 的优先级与启停 | 本设计第四节 |
| 本体 | 窗口/屏幕/输入/进程 的开关与权限 | 本设计第三节 |
| 变压器 | 压缩开关、快速输出开关、档位 | 本设计第一节 |

### 6.4 纪律

- **密码不落盘**：dashboard 会话走"现场输入 → 换 token → 只留内存"。
  设置面里**不放明文密钥输入框的回显**，也不把 key 写进任何仓内文件。
- **设置面只做配置，不做执行**：真正的调用仍走 `run_task`，不绕门。
