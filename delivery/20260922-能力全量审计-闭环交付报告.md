| 维 | 含义 | 结果 |
|---|---|---|
| A | 注册表 ↔ api 路由 | **0 问题** |
| B | 模块清单 ↔ 导入 | **0 问题** |
| G | 相对导入 ↔ 磁盘（断链） | **0 问题** |
| H | **注册表 ↔ 运行时（全能力可达，无僵尸）** | **0 问题** |
| X | 多扫描器互证 | **0 问题** |
| W | 家根影子 ↔ 真身 | **2 条**：根级 `deploy/`、`tools/` 与 `gbt_allinone/` 内同名 |
| D/E/F/V | 文档对账 / 测试数 / 审计幽灵 / 视图对账 | ⚠ **未实装**（只在 docstring 里声明过） |

**W 维那 2 条的实情**：根级 `tools/`（337 个文件，是我们自己的脚本区）
与 `gbt_allinone/tools/`（框架的工具包）**同名**。看着像"影子"，实际是两个不同东西。
但它确实有**潜在的 import 遮蔽风险**（`exposure=latent`，扫描器自己的措辞）。
⇒ 处置建议：**不改名**（改名会断掉一堆引用），但在文档里写清两者分工；或后续把根级脚本区
收进 `tools/` 之下再分一层。**这条留给 Owner 定。**

**D/E/F/V 四维未实装**：这是"文档声称 10 维、实际只有 6 维"的老问题。
已在之前修正为**分别报 `dims_implemented` / `dims_unimplemented`**，不再假装十维俱全。

## 七、诚实边界（不许当做过）

1. **这次实调用的是隔离 store**（`%TEMP%\gbt_smoke_store`），不是生产 store。
   好处：零副作用、不污染生产。代价：某些能力在空库里只能报"还没东西"，不能算全功能验证。
2. **27 个 `denied` 不等于"不能用"** —— 它们要授权。**我给不了自己授权**（grants 全 0，
   这是门纪律）。要验它们的真实执行力，需要主人在终端发一次性授权。
3. **D/E/F/V 四维没实装**，所以"十维交叉验证"目前只有六维是真的。
4. **104 个能力没有门**（第③关）—— 这是缺口，不是成绩。
5. 本次没测**带参数的实际业务闭环**（如 `wf_define`→`wf_run` 全链），只测了空参可达性。
