## 四、顺手挖出的真 BUG（本轮最有价值的发现）

跑通脉冲时，返回信封里出现：
```
"devour": {"ok": false, "error": "'list' object has no attribute 'values'"}
"stage_errors": {}          <- 空的！
"ok": true                  <- 顶层还说成功
```

### 根因（两层，都实测过）

**D1 · 类型契约不匹配 —— 吞噬第一段一直是死的**
- `scan_gaps()` 返回 `"gaps"` 是 **list**：`devour.py:224` `[{"domain": g, ...} for g in gaps]`
- 但 `quick_devour()` 写的是 `gaps["gaps"].values()`：`devour.py:400`
- 对 list 调 `.values()` ⇒ `AttributeError`
- 而 `quick_devour` 整个被 `try/except` 包着，异常被**吞成返回值** `{"ok": False, ...}`
- ⇒ **「吞噬」这一段一直是死的，而且没有任何地方报警。**

**验证它不是我测试环境的毛病**：在**真 store** 上单独跑 `get_devourer().quick_devour()`
→ 同样报 `{"ok": false, "error": "'list' object has no attribute 'values'"}`。
**是真 bug，不是环境。**

**D2 · 段内自带失败没被算成失败（假成功）**
- `devour_pulse` 只写 `except`，而 D1 的失败**不抛异常**、只在返回值里说 `ok:false`
- ⇒ `stage_errors` 空、顶层 `ok: true` —— **账面全绿，里头是死的**

### 修法
- D1：按真实类型处理（list / dict 都认）。
- D1 附带**故意不改**的东西：`domains_expected` 里还留着 `finance / wallet / ledger`，
  而那三域是主人 2026-09-12「资金能力注册清零」**明确去掉**的。
  修好类型后若让 `auto_create_from_gaps` 跑起来，它会把这三个域**自动造回来** —— 那是抗命。
  所以保持 `high_gaps` 为空 ⇒ 自动建 cap 保持关闭。**这一条留给 Owner 定**（见第六节）。
- D2：把「值里自报失败」一并收进 `stage_errors`。

### 修完复验
```
quick_devour()        -> {"ok": true, "total_found": 2, ...}      ← 活了
devour_pulse()        -> stage_errors = {}  六段全在              ← 且这次是真的空
万能插 pulse          -> devour.ok=true ; knowledge_base ok=true productive=true energy=6
```

## 六、Owner 已定：知识库必须**封死**（「只能是你的资料不能混入其他资料」）

针对原第 2 问，Owner 2026-09-22 定调：**只能是我们自己的资料，外来的一律不许混入**。
已落成**可证明的准入控制**，不是"注意一下"。

### 6.1 三道硬闸

| # | 闸 | 实现 |
|---|---|---|
| 1 | **白名单默认拒** | `SOURCE_ALLOWLIST = (codex, gbt, gbt_allinone, owner)`。名单外**一律拒**。用白名单不用黑名单 —— 黑名单只能挡住已经想到的，白名单连没想到的一起挡 |
| 2 | **投递方是"看出来的"，不是"自报的"** | `_caller()` 翻调用栈，取第一个不在 `knowledge_base.py` 里的帧，记 `模块:函数:行号` 为 `admitted_by`。投递方自己在 payload 里写的 `admitted_by` **不采信** |
| 3 | **封印审计 `verify_seal()`** | 逐条验：source 在白名单 / 有 `admitted_by` / `sealed is True`；外加**跨树污染检查** —— 知识库里不许出现 `devoured` 那棵树的东西 |

### 6.2 与「吞进来的」那棵树**物理分开**

```
store/knowledge/   ← 本知识库（只放我们的）
store/devoured/    ← 吞噬吞进来的**外部**知识（别人的，另一棵树）
```
`verify_seal()` 会检查知识库目录里有没有混入 `devoured` 路径，有就判不干净。

### 6.3 拒收也留痕

被挡下的外来投递写进 `store/knowledge/rejected.jsonl`（时间 / 来源 / 投递方 / 正文开头）。
**不然"有人想混进来"这件事根本看不见。** `verify_seal()` 会报出被拒次数。

### 6.4 实测（不是声明）

```
① 外来资料全被挡（白名单默认拒）
  source='devour_github' -> ok=False [外来] 来源被识别为外部资料（devour/devour_github）
  source='devour'        -> ok=False [外来]
  source='github'        -> ok=False [外来]
  source='external_llm'  -> ok=False [外来]
  source='unknown'       -> ok=False [外来]
  source=''              -> ok=False [缺源] 无源不收

② 我们自己的进得来
  codex / gbt / gbt_allinone:codex_bridge / owner   -> 四条全 ok=True

③ 干净库    -> sealed=True · 查了 4 条 · 被拒外来 5
④ **关键**：手工把一条 source=devour_github 的记录**绕过 deposit 直接写进 raw/**
   -> sealed=False，违规 2 条（外来来源 + 缺 admitted_by）
   -> 并且 pulse() 的 stage_errors 里出现 "seal" 报错
   ⇒ 审计器**抓得到**污染，不是橡皮图章
⑤ 删掉那条注入记录 -> sealed 重新 True
```
